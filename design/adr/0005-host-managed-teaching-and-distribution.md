# 0005 — Teach in the working conversation; install one product package

**Decision for the next candidate.** Retain [0004](0004-conceptual-explanation-and-native-integration.md)'s teaching objective and evidence discipline. Supersede its isolated Manual and Light transports, route grants, and discovery assumptions. This decision is not a new claim about the [published v0.1.0](https://github.com/taibenvenuti/elivibe/releases/tag/v0.1.0).

## One conversation, two kinds of text

The technical report is the source account, not independent proof. Explain beside it. For an existing report, keep the original message in place. When Light or Full teaches during generation, distinguish the explanation in that answer; there is no counterfactual baseline whose bytes can be compared. A follow-up can refer to an explanation without making it evidence of system behavior. Preserve opt-outs, requested formats, negative results and uncertainty. Never run a tool to fill in a gap in the source.

Make the ordinary host turn the default and only native inference path. An explicit command starts a normal conversation turn; chat history can reach the active host model. This deliberately **does not provide report-only isolation**. OMP owns routing, authentication, permissions, context management, billing and the response. An extra transport or an implicit fallback would present a second disclosure boundary. Retire the side client, Jev judge and route approvals rather than keeping inert controls or transferring old grants. If report-only disclosure matters, don't use the ordinary command on that conversation.

Manual is the default. Off and Manual do not inject lessons automatically. Light asks the ordinary model to teach selectively. Full asks for teaching with meaningful technical handoffs; neither mode adds a background judge. The explicit command works in every mode. Depth only changes teaching detail. Commands and preferences belong to the adapter; never put routing, secrets or activation state in the [portable methodology](../../skills/elivibe/SKILL.md).

OMP 19.2.1's [extension API](https://github.com/can1357/oh-my-pi/blob/v19.2.1/docs/extensions.md) supports starting a conversation turn. `sendUserMessage` skips prompt-template expansion. Do not send a literal skill command or put source text into system instructions. Apply canonical trusted guidance scoped to the applicable turn, retain host and other extensions' instructions, and attribute extension-generated scaffolding. Do not change the session-wide tool list. Keep the [implemented boundaries and limitations](../../docs/integration.md) explicit. Use the [host's skill frontmatter](https://github.com/can1357/oh-my-pi/blob/v19.2.1/docs/skills.md) to prevent automatic model selection without disabling explicit use.

## Package the files the host loads

Use the same `elivibe` root product identity and regular `skills/elivibe/SKILL.md` for a Git ref, npm package and release plugin archive. Publish only allowlisted runtime and public metadata; no consumer build step, install scripts, Python toolchain or symlink contract. Retain a standalone ZIP with the same skill. OMP is the only native integration; package-manager metadata is not evidence for Pi or Claude support.

`v0.1.0` is already public. Never move its tag, replace its assets or use the same version for different bytes. Prepare 0.2.0 for owner review as a feature release; document retired experimental commands and the change in disclosure boundary. Keep [distribution gates](../../docs/status.md) separate: building a tarball doesn't put it on npm; an authenticated preview doesn't publish a release. Reconsider another host when its packaging, activation, privacy and removal can actually be exercised.
