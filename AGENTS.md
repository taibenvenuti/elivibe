# Working on eliVibe

Start at the [status ledger](docs/status.md) for the stable release, evidence and next task. [ADR 0005](design/adr/0005-host-managed-teaching-and-distribution.md) controls activation, disclosure and packaging. Keep the published `v0.1.0` and `v1.0.0` tags and assets unchanged. Old Manual/Light side requests and route grants are **not** the current design.

- **Teaching:** edit [the single portable skill](skills/elivibe/SKILL.md). Keep the ordinary technical report intact as the source account, not verified truth. Explain mechanisms and consequences. Distinguish observation from expectation, planned from performed, and a prior interpretation from evidence. Respect formats, opt-outs and trivial cases. No tools or repo scans just to explain.
- **Host behavior:** see [integration](docs/integration.md) and [privacy](docs/privacy.md). `/elivibe` and follow-ups use ordinary OMP conversation, including its context, authentication and policies. Manual is the default; depth is independent of activation. Never add a second client, credential, grant, mandatory wizard or hidden fallback to the basic path.
- **Consumer journey:** [installation](docs/installation.md), [tested compatibility](docs/compatibility.md), [reader feedback](CONTRIBUTING.md). Prefer the verified GitHub tag or release archives in public instructions. Do not advertise a public npm install until the exact registry version and real OMP use are verified. Keep one product manifest and regular discovery files across distribution routes.
- **Checks and delivery:** [development](docs/development.md), [release procedure](docs/release.md). Test a representative teaching handoff, not only command wiring. Label authored examples, synthetic responses, live output and reader observations separately. Use cleared synthetic inputs only; keep private research, credentials and raw transcripts out of Git, CI and distributions. Project-local work never authorizes changing trust, shared profiles or publication.
