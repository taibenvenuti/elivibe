# Working on eliVibe

Start at the [status ledger](docs/status.md) for stable routes and the accepted 1.1.0 audit. The next milestone is voluntary early adoption; use [actual reader feedback](CONTRIBUTING.md) to guide improvements. [ADR 0006](design/adr/0006-one-skill-host-owned-invocation.md) defines the product boundary; [ADR 0005](design/adr/0005-host-managed-teaching-and-distribution.md) controls the Oh My Pi (OMP) adapter. Keep v0.1.0, v1.0.0 and v1.1.0 tags and assets unchanged. Old Manual/Light side requests and route grants are **not** the current design.

- **Teaching:** edit [the single portable skill](skills/elivibe/SKILL.md). Keep the ordinary technical report intact as the source account, not verified truth. Explain mechanisms and consequences. Distinguish observation from expectation, planned from performed, and a prior interpretation from evidence. Respect formats, opt-outs and trivial cases. No tools or repo scans just to explain.
- **Host behavior:** the skill is the product. The host owns invocation, context, model, authentication, permissions and ordinary follow-ups. Only OMP has executable integration and persistent modes. Keep Codex and Claude Code packaging declarative; don't port OMP's parser, add a second client, or claim a skill instruction vetoes tools. See [integration](docs/integration.md) and [privacy](docs/privacy.md).
- **Consumer journey:** [installation](docs/installation.md), [tested compatibility](docs/compatibility.md), [reader feedback](CONTRIBUTING.md). Keep one canonical teaching file. Verify real discovery and lifecycle for each install route; a valid manifest, registry publication and directory approval are different facts.
- **Checks and delivery:** [development](docs/development.md), [release procedure](docs/release.md). Test a representative teaching handoff, not only command wiring. Label authored examples, synthetic responses, live output and reader observations separately. Use cleared synthetic inputs only; keep private research, credentials and raw transcripts out of Git, CI and distributions. Project-local work never authorizes changing trust, shared profiles or publication.
